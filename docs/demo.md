# Demo per GitHub Pages

Una versione dell'app che gira **tutta nel browser** (nessun dato vero, nessun servizio). Serve per far vedere design e funzioni, anche da iPhone.

**Password e dati.** La demo pubblicata si apre con una schermata della password (sfondo da campo di calcio, titolo «Area soci», pensata per non dare nell'occhio; la scheda del browser dice «Area soci · Calcio» dal primo istante, anche mentre la pagina si carica, e «<vista> · Fuorigioco» solo dopo l'accesso: `TITOLO_PRIMA_DELL_ACCESSO`, non più «Fuorigioco · demo»): la password è `123` (`ui/src/demo/accesso.ts`). Essendo un sito statico è solo un cancello nel browser, non protegge niente di segreto; si ricorda per la sessione della scheda. **Parte vuota**: nessun dato inventato (solo «Sede principale»), e il generatore dei dati di prova non entra nella build pubblicata (resta nel codice solo per i test). Chi aveva la demo di prima riparte vuoto. Le sezioni qui sotto descrivono il comportamento del servizio finto e i dati di prova che i test generano.

- Si costruisce con `npm run build:demo` (in `ui/`): modalità `demo` di Vite (`ui/.env.demo`, `VITE_DEMO=1`), cartella `ui/dist-demo/` (ignorata da git), percorsi relativi e router con `#` perché la pagina sta in una sottocartella di GitHub Pages.
- Il «servizio» finto è in `ui/src/demo/`: `installa.ts` intercetta le chiamate `/api/...`, `backend.ts` le gestisce con gli stessi contratti di [`api.md`](api.md), `stato.ts` genera i dati di prova (circa cinque mesi, rigenerati ogni giorno) e li ricorda nel browser (`localStorage`), `xlsx.ts` costruisce il file Excel (con gli stessi formati di cella del servizio, vedi «Formati di cella»).
- L'app vera non cambia: il codice della demo non entra nella build normale.
- **Non disponibili nella demo** (rispondono con un messaggio): allegati, copie di sicurezza e ripristino. Per gli **allegati** la demo lo dice due volte (`util/allegatoDemo.ts`, solo con `VITE_DEMO=1`; l'app vera non cambia): sotto il campo «Foto» / «Allegato» e nella scheda «Allegato» del dettaglio, prima di scegliere il file, c'è «Nella demo gli allegati non si salvano.»; salvando un nuovo movimento con un file l'avviso è «Movimento salvato. Nella demo l'allegato non si salva.» (non in rosso: il movimento è salvato); se invece il file scelto era stato **rifiutato** dal campo (formato non ammesso) e si salva lo stesso, l'avviso è «Movimento salvato. File «…» non accettato.» (la frase sulla demo non si ripete: è già sotto il campo; nell'app vera finisce con «Puoi aggiungerne un altro dal dettaglio.»; vedi `interfaccia.md`, «Allegato rifiutato»). I testi della demo sono corti apposta: a 320 px l'avviso sta in tre righe anche nella variante più lunga («Movimento diviso fra 2 sedi. Nella demo l'allegato non si salva. Ora vedi settembre 2026.»). L'importazione non legge i file scelti: mostra sempre le stesse fatture di esempio (pulsante «Prova con fatture di esempio»). Nel dettaglio di una fattura importata il riquadro dice «Importata dal file della fattura elettronica» e sotto «Importata l'11/11» (con «l'» davanti a 1, 8 e 11, «il 03/11» per gli altri giorni), senza «il file resta allegato» (nell'app vera c'è: `testiFatturaImportata` in `util/allegatoDemo.ts`). **«Creato»** (`creatoIl`) di un movimento registrato nella demo, a mano o importato, è il momento in cui lo si registra, come nel servizio; solo i dati di prova restano «creati» il giorno della loro data. **Impostazioni › Dati e copie** nella demo ha tre righe senza pulsanti (`util/datiECopie.ts`): «Dove sono i dati: Solo su questo dispositivo, mai online», «Copie di sicurezza: Nella demo non si fanno. Nell'app vera se ne fa una ogni notte alle 03:00 e puoi farne una quando vuoi.», «Programma: Fuorigioco · demo» (`programmaEVersione`; il nome viene da `NOME_PROGRAMMA`); l'app vera non cambia.

## Pubblicare

La demo sta nel ramo `gh-pages` (solo i file costruiti), servito da GitHub Pages: `https://gianlucacelante.github.io/contabilita-matteo/`.

```
cd ui && npm run build:demo
# poi copiare il contenuto di ui/dist-demo nel ramo gh-pages (radice) e fare il push
```

## Sedi nella demo

La demo parte con tre sedi inventate (Via Roma, Lungomare, Mercato) e movimenti plausibili per ciascuna, così selettore, «Per sede» e «Tutte, dividi» si vedono subito. Il servizio finto (`ui/src/demo/backend.ts`) segue il contratto delle sedi di [`api.md`](api.md): `/api/sedi`, filtro `sedi`, `perSede` nel riepilogo, `/api/movimenti/dividi` (resto ai primi), `sedeId` in creazione, modifica e importazione, colonna «Sede» nell'esportazione. Archiviando le sedi fino a lasciarne una sola l'app torna identica a prima.

**Sede personale** (come «Sedi» di [`api.md`](api.md)): ogni sede ha `personale` (`false` per le sedi di prova e per quelle salvate prima: `migraStato` lo aggiunge, senza cambiare la chiave dei dati). `POST /api/sedi` e `PUT /api/sedi/{id}` accettano `personale`; 409 se l'ultima sede attiva non personale diventerebbe personale o verrebbe archiviata lasciando solo sedi personali. Senza `sedi` movimenti, riepilogo, statistiche per voce ed esportazione considerano solo le sedi non personali (con `sedi` esplicito anche le personali); «dividi» senza `sedi` esclude le personali; pizze e ordini non le considerano mai (400 «La sede «…» è personale: non ha pizze e ordini.» nell'inserimento). Test: `ui/src/demo/personale.test.ts`. Anche `GET /api/statistiche/voci` restituisce `tipo` (il tipo effettivo, come il servizio; test in `ui/src/demo/voci.test.ts`). I dati salvati nel browser hanno la chiave `contabilita-demo-v8` (oggi; prima v7 e v5): chi aveva la demo di prima riparte dai nuovi dati di prova.

## Statistiche nella demo

Il servizio finto risponde anche a `GET`/`PUT /api/statistiche/settimana`, `PUT /api/statistiche/giorni`, `GET /api/statistiche` e `GET /api/statistiche/serie`, con le regole 1–5 di [`api.md`](api.md) («Statistiche»; codice in `ui/src/demo/statistiche.ts`, instradamento in `backend.ts`): due modi di inserimento, giorni o totale settimanale, uno solo per sede e settimana (salvare l'uno cancella l'altro; il totale conta nel suo lunedì), i tre ricavi (`ricaviTotaliCent`, `ricaviExtraCent`, `ricaviConDatiCent`), scontrino medio sui soli giorni con dati e ordini, «mancante» solo senza nessun giorno né totale, serie per giorno/settimana/mese tagliata al periodo e al massimo 400 intervalli, stessi errori 400 e tutto o niente. Test in `ui/src/demo/giorni.test.ts` (gli stessi casi dei test del servizio) e `ui/src/demo/statistiche.test.ts`. La serie ha anche `daTotaleSettimanale` per intervallo e `perSede` sulle date esatte, come il servizio (test in `ui/src/demo/serie.test.ts`). Risponde anche a `PUT /api/statistiche/settimana-completa` (giorni e totali di più sedi in un solo salvataggio, tutto o niente; test in `ui/src/demo/settimanaCompleta.test.ts`) e segue la regola 3 sullo scontrino: `null` (cella vuota nei fogli) con ordini ma senza ricavi (test in `ui/src/demo/scontrino.test.ts`).

Dati di prova inventati: le ultime tre settimane intere e la settimana in corso (fino a oggi) sono inserite **giorno per giorno** per le tre sedi; il giorno di chiusura di ogni sede (Via Roma il martedì, Lungomare il mercoledì, Mercato la domenica) resta vuoto, così si vede che non genera avvisi. Le quattro settimane prima hanno il **totale settimanale** (cinque settimane fa il Lungomare manca), così si vedono entrambe le fonti. Nella settimana in corso il Mercato non è ancora stato inserito, così il banner «Manca la settimana…» si vede subito. Gli ordini si ricavano dagli incassi (del giorno o della settimana) e da uno scontrino tipico per sede (circa 20 € Via Roma, 24 € Lungomare, 17 € Mercato), le pizze da un numero tipico di pizze per ordine. L'Excel finto ha anche i fogli «Statistiche» (solo se nel periodo c'è almeno un dato) e «Pizze per giorno» (solo se ci sono giorni inseriti), con le colonne del servizio; il CSV no.

I dati di partenza sono pensati per mostrare **risultati in positivo**: ogni sede ha un giorno di chiusura diverso (Via Roma il martedì, Lungomare il mercoledì, Mercato la domenica), le retribuzioni sono **settimanali** (il sabato, sei dipendenti) e non più mensili, e affitto e bollette cadono in giorni scelti all'indietro da oggi (almeno 18 giorni fa), così non finiscono mai nella settimana in corso né in quella scorsa. Un test (`ui/src/demo/statistiche.test.ts`) simula 62 giorni di partenza diversi e controlla che settimana in corso, settimana scorsa e mese (dall'8 del mese) siano in positivo per ogni sede. Nei primissimi giorni del mese il risultato del mese può essere piccolo o in rosso (poche vendite e una fattura bastano): per questo il test controlla il mese dall'8. A inizio settimana il risultato è piccolo ma positivo nei casi provati; la settimana in corso è più alta della media perché le paghe arrivano il sabato.

## Categorie nella demo (senza predefinite)

Il servizio finto segue il contratto delle categorie di [`api.md`](api.md): nessuna categoria è predefinita né «di sistema» e non esiste più `personalizzata`. `GET /api/categorie` restituisce `{id, nome, tipo, retribuzione, usi}`; `POST` (201, o 200 con quella che c'è se il nome esiste già nello stesso tipo, e allora il flag non cambia) accetta `retribuzione`, vera solo per `COSTO_FISSO` (400 altrimenti); `PUT /api/categorie/{id}` accetta `{nome?, retribuzione?}` (almeno uno; 400 se `retribuzione=true` su una categoria non di costo fisso o valore non booleano; 409 «Questa categoria ha già delle retribuzioni.» se si toglie il flag a una categoria usata da movimenti `RETRIBUZIONE_*`; 409 per un nome già usato nello stesso tipo; tutto o niente). Una categoria nata al volo da un movimento è una categoria come le altre, e nasce sempre con `retribuzione=false` (per una nuova retribuzione si crea prima la categoria con `POST /api/categorie {…, retribuzione: true}`).

**Retribuzione e categoria** (come `api.md`): per un `COSTO_FISSO` il documento `RETRIBUZIONE_*` e una categoria con il flag vanno sempre insieme. Valgono per `POST`/`PUT` di un movimento (anche con ambito `QUESTO_E_PROSSIMI`), per le ripetizioni e per «Dividi»: `RETRIBUZIONE_*` senza categoria → 400 «Una retribuzione ha bisogno di una categoria di tipo retribuzione.»; con una categoria senza flag (o nuova) → 400 «La categoria «X» non è una retribuzione.»; `NESSUNO` con una categoria con il flag → 400 «La categoria «X» è una retribuzione: scegli Regolare o Extra.». Il controllo è `controlloRetribuzione` in `ui/src/demo/backend.ts`; i dati di partenza lo rispettano. Test: `ui/src/demo/retribuzione.test.ts`.

Il **Riepilogo** ha la forma nuova: `voci` con una riga per categoria (+ «Senza categoria», `id: null`, in fondo), ordinate per importo decrescente poi nome, e le somme per documento come «di cui» (non sommate); la nota di credito riduce la riga della sua categoria. Il foglio «Riepilogo» dell'Excel finto è quello del servizio (vedi sotto, «File esportato uguale a quello del servizio»).

Dati di partenza (nomi inventati, tutte categorie ordinarie): ricavi **Sala** (incassi del giorno), **Asporto** (extra), **Delivery**, **Eventi**; costi variabili **Ingredienti** (farine, latticini, verdure, conserve, salumi), **Bevande**, **Carta e contenitori**, **Imballaggi**, **Pulizia**, **Manutenzione**; costi fissi **Affitto, Luce, Gas, Internet, Assicurazioni, Pulizie, Commercialista** e **Retribuzione** (l'unica con `retribuzione=true`, si rinomina, ad esempio in «Paghe»). Quasi ogni movimento ha la categoria; restano senza (riga «Senza categoria») gli scontrini del sabato e un extra al mese. Importi piccoli rispetto agli incassi: i risultati restano positivi (test in `statistiche.test.ts`). Test: `ui/src/demo/categorie.test.ts`. Chiave dei dati salvati alzata a `contabilita-demo-v7` (forma diversa: `retribuzione` al posto di `personalizzata`).

**Nota di credito a mano (novembre 2026).** Il servizio finto la accetta come quello vero: `NOTA_DI_CREDITO` solo per `COSTO_VARIABILE` (400 per ricavo e costo fisso), `pagata` sempre `false`, `PUT /movimenti/{id}/pagata` → 400; riduce totali dell'elenco, Riepilogo (riga della categoria e «Fatture»), `fattureCent` delle statistiche per fornitore e il «Da pagare» di Ricevute, come una nota importata (`ui/src/demo/notaDiCredito.test.ts`).

**Importazione: doppioni e tipo di documento come nel servizio (novembre 2026).** Le fatture d'esempio dell'anteprima sono **dieci**: sette fatture, una nota di credito («DEMO-8 NC»), un'integrazione («DEMO-9») e una **nota di debito** («DEMO-10 ND», segnata «Nota di debito», che si importa come una fattura pagata). Ognuna ha `tipoDocumento` e `notaDiDebito`, come in [`api.md`](api.md). Una fattura d'esempio è «già registrata» con la regola del servizio (`giaRegistrata` in `ui/src/demo/backend.ts`): stesso **documento** (`FATTURA`, o `NOTA_DI_CREDITO` per la nota di credito), stesso fornitore (senza badare alle maiuscole), stesso numero e stessa **data**; prima bastavano numero e fornitore, quindi una nota di credito registrata a mano con il numero di una fattura la faceva risultare doppia. Vale all'anteprima e alla conferma. Siccome conta la data, le date delle fatture d'esempio **non seguono oggi giorno per giorno**: sono «N giorni prima» (da 2 a 12) di un giorno di ancoraggio salvato nello stato (`dataEsempi`). L'ancoraggio resta fermo finché almeno una fattura d'esempio è registrata con quelle date, così nei giorni dopo quelle importate restano «Già registrata» e non si registrano due volte (nella demo pubblicata i dati restano nel browser); quando non ce n'è nessuna (prima lettura, o tutte eliminate) torna a oggi, così le date sono recenti. Dopo l'importazione l'avviso «Ora vedi …» porta comunque al mese di quelle date, anche se l'ancoraggio è di qualche settimana prima. La demo non legge i file, quindi non ha i limiti di dimensione del servizio.

**«includi» come nel servizio (novembre 2026).** `GET /api/esporta` senza `includi`, o con `includi` vuoto, esporta **tutti i tipi** sia nel CSV sia nell'Excel, come `EsportazioneService.tipiDa` (prima la demo dava la sola intestazione); un valore che non è un tipo → 400 «includi: valore non valido: X»; di sole virgole (`includi=,`) nessun tipo, quindi la sola intestazione, come `String.split` in Java. L'anteprima dell'importazione mostra lo scarto con il testo del servizio, senza sigle: «Autofattura di integrazione: non importata, la fattura originale del fornitore è già una fattura a parte.».

**Parametri di «esporta» controllati come nel servizio (novembre 2026).** `GET /api/esporta` della demo fa gli stessi controlli del servizio, nello stesso ordine, con gli stessi testi e lo stesso 400 (elenco in [`api.md`](api.md), «Esportazione», «Controlli sui parametri»): prima i valori che non si leggono (`da`, `a`, `statistiche`, `colonnePerSede` → «da: valore non valido: marzo»), poi `sedi`, poi `formato` («formato: deve essere xlsx o csv»: prima un formato sconosciuto o assente dava un CSV), poi le date («Servono entrambe le date: da e a.», «La data iniziale non può essere dopo quella finale.»: prima usciva un file vuoto), infine `includi`. I sì/no si leggono come nel servizio (`true`/`on`/`yes`/`1`, `false`/`off`/`no`/`0`, vuoto = valore predefinito; prima contava solo il testo esatto `true`/`false`). Codice: `parametriEsporta` ed `esportaFile` in `ui/src/demo/backend.ts`. Test: `ui/src/demo/esporta.test.ts` («i parametri di «esporta» si controllano come nel servizio»), con gli stessi casi di `EsportaApiTest`. L'interfaccia manda sempre parametri validi: per chi usa la demo non cambia niente.

**File esportato uguale a quello del servizio.** CSV e foglio «Movimenti» dell'Excel hanno le colonne del servizio nello stesso ordine (`Data`, `Tipo`, `Documento`, `Categoria`, `Fornitore`, `Dipendente`, `Descrizione`, `N. documento`, `Note`, `Importo`, `Origine`, `Sede`) e le stesse etichette in italiano: Documento «Fatturato», «Extra», «Fattura», «Nota di credito», «Scontrino», «Retribuzione regolare», «Retribuzione extra», «-»; Origine «A mano», «Fattura elettronica» (per i movimenti importati; prima «XML»), «Ricorrenza» (prima uscivano i valori degli enum, `NOTA_DI_CREDITO`, `MANO`, in un ordine diverso e senza `Note`). Colonne ed etichette stanno in un posto solo, `ui/src/api/esporta.ts` (`INTESTAZIONI_FILE`, `TIPO_FILE`, `DOCUMENTO_FILE`, `ORIGINE_FILE`, `testiRigaFile`), usato sia dall'anteprima di «Esporta» (per l'Excel come per il CSV: anche il Tipo è «Costo variabile», non più «variabile»; solo l'importo dell'anteprima Excel è scritto come lo mostra Excel in italiano col formato valuta del file, `-1.234,50 €`; nel CSV resta `-1234,50`) sia dal servizio finto; vanno tenute uguali a `EsportazioneService` (`INTESTAZIONI`, `etichetta`). Nel CSV un campo va tra virgolette anche per un solo `\r`, come nel servizio. Test: `ui/src/demo/esporta.test.ts`.

**Foglio «Riepilogo» uguale a quello del servizio** (`EsportazioneService.voci` e `scriviRiepilogo`): riga 1 «Riepilogo dal 2026-11-01 al 2026-11-30», riga 2 vuota, riga 3 l'intestazione «Voce | Importo», poi nell'ordine: una riga per categoria dei ricavi (solo il nome della categoria), «Totale ricavi», «Ricavi fatturati», «Ricavi extra»; le categorie dei costi variabili, «Totale costi variabili», «Fatture», «Scontrini»; le categorie dei costi fissi, «Totale costi fissi», «Retribuzione regolare», «Retribuzione extra»; «Costi», «Risultato». Le righe per documento ci sono sempre, anche a zero. Gli importi hanno il segno di `GET /api/riepilogo`: **i costi sono positivi** (solo «Risultato» può essere negativo, e la riga di una categoria con più note di credito che fatture). Il foglio non dipende da `includi`, come nel servizio. Prima la demo scriveva «Ricavi: Sala», «  di cui fatturati» (solo se maggiori di zero), i costi in negativo e una prima riga «Periodo». Nomi delle righe e costruzione del foglio stanno in `ui/src/api/esporta.ts` (`RIEPILOGO_FILE`, `righeFoglioRiepilogo`), accanto alle colonne del foglio «Movimenti»; vanno tenuti uguali a `EsportazioneService`. Test: `ui/src/demo/esporta.test.ts` («il foglio Riepilogo dell'Excel è quello del servizio»).

**Formati di cella uguali a quelli del servizio** (`EsportazioneService`: `FORMATO_DATA`, `FORMATO_VALUTA`, `LARGHEZZE`, `intestazione`, `scriviRiepilogo`). Il file ha `xl/styles.xml` (dichiarato in `[Content_Types].xml` e collegato da `xl/_rels/workbook.xml.rels`, dopo i fogli) con sette stili di cella e niente altro: normale, intestazione (grassetto su fondo `D9D9D9`), data (`yyyy-mm-dd`, allineata a sinistra), valuta (`#,##0.00 [$€-410]`), valuta in grassetto, testo in grassetto, titolo (grassetto, corpo 12). In tutti i fogli:

- le **date** (colonna `Data` di «Movimenti» e «Pizze per giorno», `Settimana` di «Statistiche») sono celle data: il numero seriale di Excel nel sistema 1900 (`serialeExcel`: giorni interi contati in UTC, quindi senza fusi orari né ora legale; il 10 maggio 2031 è 47978) con il formato data. Un testo che non è una data vera resta testo;
- gli **importi** sono numeri in euro con il formato valuta; pizze, ordini e «Giorni inseriti» sono numeri semplici; lo scontrino medio che manca **non ha la cella** (prima era un testo vuoto);
- la **riga di intestazione** è in grassetto su grigio; in «Movimenti», «Statistiche» e «Pizze per giorno» è **bloccata** (resta ferma scorrendo);
- le **larghezze** delle colonne sono quelle del servizio (Movimenti 12, 16, 22, 20, 28, 20, 36, 16, 36, 14, 20, 24: la colonna «Origine» è passata da 12 a 20 per «Fattura elettronica»; Riepilogo 34 e poi 16 per ogni colonna di importi; Statistiche 12, 24, 10, 10, 14, 16, 14, 24, 18; Pizze per giorno 12, 24, 10, 10, 14, 14, 16);
- in «Riepilogo» il titolo è in grassetto corpo 12, l'intestazione «Voce | Importo» è grigia e non bloccata, e le righe dei totali («Totale ricavi», «Totale costi variabili», «Totale costi fissi», «Costi», «Risultato») sono in grassetto, nome e importi. I totali si riconoscono dal posto, non dal nome (`righeTotaliRiepilogo` in `ui/src/api/esporta.ts`): una categoria che si chiama «Costi» resta normale.

Gli stili stanno in `ui/src/demo/xlsx.ts` (`Stile`, `Cella`, `Foglio.larghezze`, `Foglio.intestazioneBloccata`); `backend.ts` dice per ogni cella quale stile ha. I caratteri di controllo che l'XML non ammette si tolgono dai testi (con uno solo Excel dichiarerebbe il file danneggiato); un testo con spazi in testa o in coda, o di soli spazi, è scritto con `xml:space="preserve"`, così gli spazi non si perdono. Il file resta uno zip non compresso. Restano diversi dal servizio solo dettagli che non si vedono (per esempio il servizio scrive anche le proprietà del documento, `docProps`). Test: `ui/src/demo/esporta.test.ts` («i formati di cella dell'Excel sono quelli del servizio»: struttura del file, coerenza di `styles.xml`, date seriali, stile di ogni cella, larghezze, blocco). Il file scaricato dalla demo è stato riaperto con Excel (senza riparazione), LibreOffice e openpyxl.

L'esportazione Excel della demo rispetta le opzioni del servizio: `colonnePerSede=true` scrive nel foglio «Riepilogo» una colonna per sede più «Totale» al posto di «Importo» (le righe sono quelle del complessivo, 0 dove una sede non ha la categoria), ma solo se le sedi del Riepilogo sono **più di una**, come nel servizio (con una sede sola resta «Voce | Importo»; prima la demo scriveva la colonna della sede e «Totale» anche così); `statistiche=false` toglie il foglio «Statistiche» (il CSV le ignora).

Il servizio finto rispetta anche il filtro `categorie` di `GET /api/movimenti` (`?categorie=3,7`: id separati da virgola, in AND con periodo, tipo, sedi e ricerca; i movimenti senza categoria restano fuori; i totali seguono l'elenco filtrato; valori non numerici ignorati). Test in `ui/src/demo/backend.test.ts`. I dati non cambiano forma: la chiave era `contabilita-demo-v5`, ora `contabilita-demo-v7`.

## Fatture da fare nella demo (da Statistiche, «Fatture»)

Il servizio finto segue il contratto «Fatture da fare» di [`api.md`](api.md): `GET/POST /api/fatture/caselle` (201, o 200 se il nome esiste già senza badare alle maiuscole), `PUT` (rinomina, 409 per un nome già usato), `DELETE` (204, cancella anche gli stati), `GET /api/fatture?da=&a=` (al massimo 24 mesi, `daFare`) e `PUT /api/fatture/caselle/{id}/mesi/{mese}` (400 per mese, stato, importo o nota non validi; `DA_FARE` senza importo né nota cancella lo stato salvato). Dati di partenza (nomi inventati): «Fatture eventi», «Fatture catering Rossi», «Fatture Euro Service», con mesi passati quasi tutti pagati, un paio dimenticati (da fare, in ritardo), una emessa da incassare e due «Da fare» nel mese in corso, così la scheda del Riepilogo si vede subito. **Caselle con scadenza e fatture ricevute (novembre 2026).** Le caselle hanno `dalMese` e `giornoScadenza`; `GET /api/fatture` dà per ogni mese `attiva` e `scadenza` (mese corto: ultimo giorno) e `daFare` conta solo i mesi attivi; `POST`/`PUT` accettano `giornoScadenza` (1–31, `null` la toglie) e `dalMese` (400 per valori non validi; `PUT` senza campi 400; una casella nuova parte dal mese corrente, quindi niente arretrati); `GET /api/fatture/promemoria` dà `daFare` e `inScadenza` (Da fare del mese corrente con scadenza entro 3 giorni o scaduta, per `giorniMancanti` crescente). Dati di prova: «Fatture eventi» scade il 28, «Fatture catering Rossi» **fra due giorni dalla data di oggi** (così il Riepilogo ha sempre una riga in evidenza, qualunque giorno si apra la demo), «Fatture Euro Service» il 5; le tre partono da cinque mesi fa. I movimenti hanno `pagata`: le fatture di oltre 45 giorni fa sono pagate, quelle più recenti miste (una su tre da pagare); `PUT /api/movimenti/{id}/pagata` (400 «Solo una fattura si segna come pagata.», 404), filtro `?pagata=true|false`, `pagataCent`, `fattureCent` (fatture meno note di credito, senza scontrini), `pagataPerMese` e `fatturePerMese` nelle statistiche per fornitore (null per gli altri raggruppamenti; quanto resta da pagare è `fattureCent − pagataCent`), le fatture importate da XML nascono pagate (le note di credito importate no). ## Elenchi e statistiche per voce nella demo

Il servizio finto segue i contratti «Gestione di categorie, fornitori e dipendenti» e «Statistiche per voce» di [`api.md`](api.md) (codice in `ui/src/demo/voci.ts`, instradamento in `backend.ts`). Le tre `GET` aggiungono `usi` (movimenti che usano la voce; non si salva, si calcola a ogni lettura). `PUT /api/{categorie|fornitori|dipendenti}/{id}` rinomina qualunque categoria (400 nome vuoto o oltre 120 caratteri, 404, 409 «Esiste già …» senza distinguere maiuscole; cambiano movimenti e ripetizioni). `DELETE` lascia i movimenti e le ripetizioni senza la voce; con `sostituisciCon` li sposta sull'altra voce (404 se non esiste, 400 se è la stessa o, per le categorie, di tipo diverso; tutto o niente). `GET /api/statistiche/voci`: mesi di calendario, `perMese` che somma al totale, nota di credito che riduce, riga `id: null` in fondo, ordine per totale decrescente poi nome, tipo predefinito per raggruppamento (categorie: tutti; fornitori: `COSTO_VARIABILE`, come il servizio), 400 per parametri non validi. Per i fornitori l'interfaccia chiede solo i costi variabili. `GET /api/movimenti` accetta anche i «Filtri per voce» del contratto: `fornitore=<id>` e `senza=FORNITORE|DIPENDENTE|CATEGORIA` (400 «fornitore: valore non valido…», 400 per `senza` non valido o insieme a `categorie`); per ogni riga delle statistiche la somma con segno dell'elenco filtrato è il suo totale (test: `ui/src/demo/dettaglioVoce.test.ts`). I dati di prova (nove fornitori, sei dipendenti, cinque mesi) hanno già movimenti su più mesi per ogni voce. Test: `ui/src/demo/voci.test.ts`, `ui/src/util/voci.test.ts`, `ui/src/util/statisticheVoci.test.ts`. La chiave dei dati salvati è `contabilita-demo-v7`.

**Correzioni dalla simulazione del cliente.** Statistiche per voce con `raggruppa=DIPENDENTE`: solo i movimenti con documento `RETRIBUZIONE_*` (il `tipo` si ignora, un costo fisso come l'affitto non compare nemmeno in «Senza dipendente»; `tipoPredefinito` in `ui/src/demo/voci.ts`). `GET /api/movimenti` accetta anche `retribuzione=true|false` (400 «retribuzione: valore non valido…» per altro): `true` tiene solo le retribuzioni. Il messaggio di scarto dell'importazione resta quello del servizio vero («Tipo di documento TD16 non ammesso…»): è l'interfaccia che lo traduce in una frase semplice. Test: `ui/src/demo/voci.test.ts`, `ui/src/demo/dettaglioVoce.test.ts`.

## Movimenti divisi nella demo (`divisione`)

Il servizio finto segue «Movimenti divisi» di [`api.md`](api.md). Ogni movimento ha `divisione` (`null` se non è diviso). `POST /api/movimenti/dividi` dà a tutte le parti lo stesso valore, solo se le parti sono almeno due; nella demo il valore è `demo-<id del primo movimento>` (nel servizio è un UUID: è un testo opaco, conta solo l'uguaglianza; il contatore degli id non torna indietro, quindi non si ripete). Con «Ripeti» ogni sede ha la sua ripetizione, con lo stesso `divisione` (`RicorrenzaDemo.divisione`), e le parti di ogni scadenza hanno l'id `<divisione>:<data>` (`divisioneDellaScadenza` in `stato.ts`), uno per scadenza. Modifica ed eliminazione di una parte non cambiano l'id (non è nel corpo: un `divisione` mandato nel `PUT` si ignora). Le statistiche per voce (`voci.ts`) contano le parti una volta per voce e mese; gli importi restano la somma delle parti. Il file esportato non cambia.

**Dati salvati prima.** `migraStato` mette `divisione: null` ai movimenti e alle ripetizioni che non l'hanno (come la colonna nuova del servizio, null sui vecchi dati); la chiave resta `contabilita-demo-v9`, perché la forma cambia solo per aggiunta e la migrazione è ripetibile. I dati di prova non hanno movimenti divisi. Test: `ui/src/demo/divisione.test.ts` (gli stessi casi di `DivisioneApiTest` del servizio).
